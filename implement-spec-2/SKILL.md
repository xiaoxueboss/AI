# 执行

独立完成从需求到实现的流程。使用当前对话和项目上下文；不调用或修改其他技能。先与用户确认对需求的共同理解，随后连续执行各阶段，不要求用户确认规格、工单拆分或测试方案。遇到缺失权限或无法安全继续的阻碍时，说明已完成的工作并询问或停止；不得凭空假定授权。

## 0. 逐轮澄清需求

将目标、范围、约束和关键设计选择整理为决策树。每轮找出前置决策已明确、可以立即回答的所有未决问题，编号集中提出；每题给出推荐答案，并让用户可以用“是”接受推荐。等待用户回答后，根据答案继续追问被解锁的问题。对话中已明确的决定不重复提问。

通过查看项目、文件和可用工具自行查明事实，不把可查事实当作问题交给用户。可独立开展的调查不阻塞其他问题；依赖调查结果的问题等结果明确后再问。继续处理各分支，直到没有影响目标、范围或实现的未决设计选择。简要总结共同理解，请用户确认；确认前不生成规格或进行实现。用户确认后直接进入下一阶段，无需再次确认工单。

## 1. 规格

阅读相关代码、调用方和项目规则，结合现有讨论明确目标。把精简规格写入项目的 `.scratch/<feature-slug>/spec.md`：问题、目标行为、必要的实现决策、可验证的验收条件、范围外事项。记录影响实现的假设；不编造需求。不生成冗长用户故事或预先设计测试边界。

## 2. 工单

将规格拆成最少数量的可独立验证的完整交付切片。每张工单写入 `.scratch/<feature-slug>/issues/<NN>-<slug>.md`，按依赖顺序编号，包含交付内容、验收条件、阻塞工单和状态。只标注真实依赖；小任务可以只有一张工单。检查覆盖所有验收条件且依赖无环，然后直接采用拆分结果，无需询问用户。

## 3. 实现

把工单视为依赖图，优先并行执行所有依赖已完成的工单。每张工单交给一个全新上下文的实现子智能体，提供规格和工单路径、基准提交及必要约束，包括不调用其他技能、不强制 TDD 和按风险验证。各子智能体在独立 worktree 和分支工作，基于当前集成分支，实现工单并执行必要验证，汇报变更、检查和风险。主智能体在集成分支逐项整合结果，解决冲突并更新工单状态；依赖解除后启动后续工单。不要在共享 worktree 中并行修改。

开始前检查 Git 状态，保护已有改动；以仓库已有的 `master` 为开发基准、集成和最终交付分支，没有 `master` 时使用当前分支，不另建集成分支。子智能体需要隔离时，从集成分支创建临时分支及 worktree，不覆盖用户数据。临时分支与 `master` 并列，默认使用 `codex/功能名`，项目有其他前缀要求时遵循项目规则，不使用 `master/功能名`。在当前 Git 仓库根目录的 `临时工作区` 下，为每个新工作区使用独立且不冲突的子目录；无写入权限时停止并询问用户新位置。分支名称的用途部分和工作区子目录用不超过 15 个汉字简述用途，冲突时加数字区分。若环境不支持子智能体或隔离 worktree，说明限制并顺序完成工单，不假称并行。若合并、环境或权限阻碍进展，保留成果并报告，不使用破坏性命令强行继续；不要将用户无关改动纳入提交。

## 4. 验证与交付

根据改动风险和项目要求选择最小充分验证，复用现有检查；必要时补充有意义的测试。无需 TDD、先写测试、预先确认测试边界或为每张工单强制新增测试。汇总后检查整体变更是否符合规格、项目约定和验收条件，修复发现的问题，再运行适当的最终检查。记录未运行的检查及原因。

完成并验证后，将成果安全整合到交付分支，清理本流程创建且已安全整合的 worktree 和临时分支，使本次流程不遗留额外分支；不删除原有分支。保留未整合的工作，清理受阻时说明原因；报告规格和工单路径、交付分支、实现结果、验证结果及未解决风险。除非用户明确要求，不发布工单、推送、创建或合并 PR、部署或关闭远程事项。
